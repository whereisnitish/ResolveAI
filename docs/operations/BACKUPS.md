# Backups and disaster recovery

## What must be backed up

| Data | Where | Loss impact | Mechanism |
|---|---|---|---|
| PostgreSQL (all tenant data, audit log, usage ledger, embeddings) | RDS / `db` container | Total | RDS automated backups + PITR, **plus** daily logical dumps |
| Uploaded files (attachments, knowledge files) | S3 bucket (or the `media` volume) | Attachments unreadable; knowledge can be re-uploaded | S3 versioning + cross-region replication or AWS Backup |
| `FIELD_ENCRYPTION_KEY` | Secrets Manager + break-glass vault | Integration URLs unrecoverable | Out-of-band copy, never stored next to the DB backups |
| `DJANGO_SECRET_KEY` | Secrets Manager | All sessions and signed tokens invalidated (users sign in again) | Out-of-band copy |
| Redis | ElastiCache | **None of lasting value.** Caches, sessions (also in DB), queued tasks, channel layer | Not backed up. Queued tasks are retried or regenerated by beat scans |

## Targets

* **RPO** (data loss): ≤ 5 minutes with RDS PITR; ≤ 24 h from logical dumps alone.
* **RTO** (time to restore): ≤ 1 h. That covers restoring the database into a new instance or database, verifying it, and repointing the app.

## Logical dumps: `infrastructure/scripts/`

| Script | Does |
|---|---|
| `backup.sh <dir>` | `pg_dump -Fc` (no owner/ACL, so it restores into any role layout), checks the archive with `pg_restore --list`, writes a `.sha256`, and prunes dumps older than `RETENTION_DAYS` (14) |
| `restore.sh <dump> <new-db>` | Verifies the checksum, **refuses an existing target database**, creates the extensions, then restores |
| `verify-backup.sh <dump>` | Restores into a throwaway database. Compares row counts of critical tables with the source, checks that the append-only triggers, the HNSW vector index and `django_migrations` came back, then drops the throwaway database |

The scripts use the standard libpq variables (`PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`). To run the client tools inside a container instead (for example, locally without a Postgres install), set `PG_CONTAINER=<container>`:

```bash
PG_CONTAINER=resolveai-db-1 infrastructure/scripts/backup.sh ./backups
PG_CONTAINER=resolveai-db-1 infrastructure/scripts/verify-backup.sh ./backups/resolveai-resolveai-<stamp>.dump
```

### Schedule (production)

* **Daily:** run `backup.sh` from a scheduled ECS task or cron. Then `aws s3 sync <dir> s3://<backup-bucket>/db/ --sse aws:kms`. The backup bucket is in a different account or region, with Object Lock (compliance mode, 35 days) and a lifecycle rule moving objects to Glacier after 30 days.
* **Weekly:** run `verify-backup.sh` against the latest dump. Alert if it fails.
* **Quarterly:** do a full DR drill. Restore RDS to a point in time into a new instance, point a staging stack at it, run the E2E suite, and record the measured RTO.

### Verified locally (Phase 5)

Run against the development database: the backup was 254 KB with 46 table-data entries. `verify-backup.sh` restored it with exact row counts on all 8 critical tables, plus 2 append-only triggers, 1 HNSW index and 41 migrations. `restore.sh` refused to overwrite the existing `resolveai` database.

## Restore procedure (incident)

1. Declare the incident and freeze writes if data is being corrupted: scale `worker` and `beat` to 0 and put the ALB into maintenance (fixed 503).
2. Pick the restore point: just before the bad change, from the audit log, application logs or Sentry.
3. **RDS PITR:** restore to a new instance at that timestamp. **Logical:** `restore.sh <dump> resolveai_restored_<date>`.
4. Verify: run `verify-backup.sh`-style counts, log in as a test tenant, open the inbox.
5. Repoint `DATABASE_URL` / `POSTGRES_*`, redeploy `backend`, `worker` and `beat`, and lift maintenance.
6. Keep the old database read-only for 7 days for forensics, then delete it with approval.
7. Write the postmortem.

## Tenant-level data requests

The audit log and usage ledger are append-only **in the database**: triggers reject UPDATE and DELETE (see [ADR-0011](../decisions/0011-database-enforced-append-only.md)). A legitimate erasure, such as GDPR/DPDP deletion of an organization, must run inside `common.db.allow_purge()` from an audited management command. Deleting a user nulls `audit_auditlog.actor_id` (the one permitted update), and the trail keeps `actor_email`.
